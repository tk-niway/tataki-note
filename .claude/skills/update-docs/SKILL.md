# 利用者ガイドを直す

利用者ガイドは、目次 `docs/README.md` と、`docs/features/` の下の機能ごとのページ。変更ごとにページを
1本足すのではなく、今あるページと目次を、変更後のアプリの姿に合わせる。開発者向けの資料は書かない。

## 何を材料にするか

呼び出し元が差分(ファイル・コミットの範囲)を渡したらそれを使う。渡されなければ:

- 作業中の変更なら、`main` から今のブランチまで(`git diff main...HEAD` と作業ツリーの変更)
- リリースの準備なら、前のリリースのタグから `HEAD` まで(`git describe --tags --abbrev=0` で前のタグ)。
  他の人の変更も含めて、ガイドに書かれていない機能・事実と違う記述が無いかを見る

差分だけでは画面の文言や動きが分かりにくければ、差分に出てきたファイルの全体・画面の View・設定の既定値を読む。

## 直し方

- **新しい機能**: 既存のページに入る機能ならそのページに節を足し、入らなければページを1つ作る。目次に項目を足す
- **変わった機能**: そのページの該当箇所だけを直す(書き直さない)。目次の説明も合わせる
- **画面の操作や見え方が変わらない変更**(内部の作り替え・テストだけなど)では、ページも目次も変えない
- **既存のページの見直し**: 全ページと目次を読み、変更で事実と違うようになった箇所を直す
  (既定値・選択肢・操作・画面の文言など)。直すのは変わった事実だけで、体裁を整えたりしない。
  見出しを変えたら、目次や他のページからその見出しへのリンク(`ページ.md#見出し`)も直す

## 書くこと・書かないこと

読者は、アプリを使う人。

- **書くこと**: 何ができるか、どこから開くか(メニューバーのどの項目・どのショートカット)、操作の手順、
  メニューの項目・キーボードショートカット・設定の項目の表、知っておくこと(制限・癖・うまくいかないときの
  通知など、利用者に関わる動き)、利用者の判断に役立つ理由(例: 既定値がそうなっている理由)
- **書かないこと**: 型名・関数名・ファイル名・コード例・保存の場所(UserDefaults のキーなど)・API の名前・
  開発の番号・変更の経緯(「〜を廃止した」「〜を追加した」「以前は」)・「更新:」「作成日:」の行・
  「要確認」のメモ・開発の都合による理由。**今の姿だけ**を書く

### TatakiNote で決めていること

- その機能をメニューバーのどこから開くか、関係するグローバルなショートカットの既定値と変え方(設定ウィンドウ)を
  書く(同じことを書いたページへのリンクでもよい)
- 画面の文言(メニューの項目・設定の項目と選択肢・ボタン)は、アプリに出ている文言のまま「」で書く。キーは
  `⌘`・`⇧`・`⌥`・`⌃`・`↩`・`esc` の記号で書き、初出で「(Command + Enter)」のように読みを添えてよい
- アクセシビリティの許可など OS の権限が要る機能は、許可が無いときにどうなるかを書く(アクセシビリティの
  ページへのリンクでよい)
- 見出しの文言を変えたら、その見出しへのリンク(`page.md#見出し`)を全ページから Grep して直す

## 事実の確かめ方

- 画面の文言(メニューの項目名・設定の項目名と選択肢・説明文・ボタン名・通知の文)は、コード(画面の View の
  文字列)から写す
- ガイドとコードが食い違うときは、コードに合わせる
- コードで確かめられない挙動を、推測で書かない。分からなければ書かない

## 目次とページの形

- **目次 `docs/README.md`**: 冒頭に、アプリが何をするものかを数行。その後、使う目的(「〜したい」)や機能の
  種類ごとの `##` のまとまり。各項目は「何ができるかが分かる短い説明 + そのページ(または節)への相対リンク」
  (例: `[設定ウィンドウ](features/settings.md)`)。**すべてのページが目次から辿れること。**
  症状から辿る「困ったとき」のまとまりは作らない
- **ページ**: `# <機能の名前>` と、何ができるかの1〜3行の後、操作ごとの `##` / `###` の節。他のページへは
  相対リンク(同じ `features/` の中なので `[設定ウィンドウ](settings.md)`、目次へは `[目次](../README.md)`)。
  同じ説明を2か所に書かず、詳しい説明を置いたページへリンクする
- **節へのリンク**は `ページ.md#見出し`。見出しの ID は GitHub の規則で作られる(英字は小文字にし、文字・数字・
  空白・`-`・`_` 以外を消し、空白を `-` にする)。リンクする見出しには記号(`・`・`+`・`(`・`「」` など)を
  使わない方が壊れにくい。1つのページで同じ見出しを2回使わない

## ファイルの決まり

- 書くのは `docs/` の中だけ。目次は `docs/README.md`、ページは `docs/features/<内容を表す英語の kebab-case>.md`
  (例: `docs/features/settings.md`)で、日付を付けない
- `docs/` の直下には目次のほかにページを置かず、`docs/features/` の中にさらにフォルダを作らない
- 単体テスト `UserDocsTests` が次を確かめる: 目次があること、ページが `docs/features/` の直下にあること、
  目次から全ページへリンクされていること、相対リンクの先(と見出し)があること、日付で始まるファイル名が
  無いこと、開発者向けの内容(`.swift`・`UserDefaults`・開発の番号など)が無いこと

## 終わったら

直したページと、直さなかった理由(変更が利用者から見えない、など)を短く報告する。呼び出し元が報告の形を
指定したら、それに従う。
